# Вопросы и решения Primal Web

Решения, принятые при проектировании, сведены в `architecture.md` §11. Здесь — вопросы и решения,
возникшие при выполнении задач плана (`implementationTasks.md`).

---

## Задача 1.1: Репозиторий и правила агента (27.09.2026)

### 1. Как устроен процесс работы с агентом?

**Решение (пользователь):** тестирование не выносится в отдельный процесс. Одна команда
`.kilo/commands/implementTask.md` выполняет задачу целиком — код и тесты. Правила — `.kilorules`.

### 2. Окончания строк

**Решение:** `web/.gitattributes` закрепляет LF для всех текстовых файлов и CRLF только для `*.bat`/`*.cmd`.
Иначе `gradlew` и `*.sh`, выгруженные на Windows, ломают сборку Docker-образов.

## Задача 1.3: Каркас бэкенда (27.09.2026)

### 3. Версии

**Решение:** Spring Boot 4.1.1 (последний выпуск на 27.09.2026), Gradle 9.8.0, Java 25. В Boot 4 стартеры
разделены по модулям: `spring-boot-starter-webmvc`, `spring-boot-starter-flyway`, тестовые
`spring-boot-starter-webmvc-test` (`org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest`);
Jackson 3 (`tools.jackson.*`); Testcontainers 2 (`org.testcontainers:testcontainers-postgresql`).

### 4. JDK 25 на машине разработчика

**Решение:** устанавливать не обязательно. Gradle запускается на любом JDK 17+, а JDK 25 для сборки
скачивает сам (плагин `foojay-resolver-convention`, `settings.gradle.kts`) в `~/.gradle/jdks`. На Windows
запускать `gradlew.bat`: скрипт `gradlew` из Git Bash отказывается работать.

### 5. Безопасность до задачи 3.2

**Решение:** временный `identity/SecurityConfig` разрешает все запросы и не создаёт HTTP-сессий. Автонастройка
пользователя по умолчанию (`UserDetailsServiceAutoConfiguration`) отключена в `application.yml`: паролей в
приложении нет, а сгенерированный пароль попадал в лог.

### 6. Переменные окружения бэкенда

**Решение:** подключение к БД — `DB_URL`, `DB_USER`, `DB_PASSWORD`; значения по умолчанию подходят для
`docker-compose.dev.yml`. В полном стеке их собирает `docker-compose.yml` из `POSTGRES_*` (задача 1.5).
Настройки приложения — `PUBLIC_URL`, `PRIMAL_OTP_PEPPER`, `PRIMAL_SHARE_LINK_KEY` (`PrimalProperties`).
Проверка здоровья SMTP отключена: недоступный почтовый сервис не должен делать сайт «нездоровым».

## Задача 1.4: Каркас фронтенда (27.09.2026)

### 7. Версии

**Решение:** React 19.3, Vite 8, Vitest 5, Mantine 9, TanStack Query 5, React Router 8, ESLint 10, orval 8,
MSW 2. TypeScript — 6.0: typescript-eslint поддерживает TypeScript до 6.0, а TypeScript 7 (новый
компилятор на Go) им пока не поддерживается.

### 8. Как проверяются границы `src/domain`

**Решение:** вместо плагина `eslint-plugin-boundaries` — встроенные правила ESLint для файлов
`src/domain/**` (`eslint.config.js`, `domainRestrictions`): `no-restricted-imports` запрещает React,
UI-библиотеки и остальное приложение (`api`, `features`, `app`, `shared`); `no-restricted-globals` запрещает
`window`, `document`, `localStorage`, `sessionStorage`, `navigator`, `fetch`. Правило проще и без
дополнительного плагина; его работу проверяет тест `src/test/eslint-domain.test.ts`. Окружение
(например, хранилище для боя в задаче 2.2) передаётся в код `src/domain` параметром.

### 9. Клиент API

**Решение:** `apiFetch` (`src/api/http.ts`) — единая точка запросов, её же использует сгенерированный
клиент orval (`includeHttpResponseReturnType: false` — функции возвращают тело ответа, ошибки — исключением
`ApiError`). Адрес запроса собирается от `window.location.origin`: в браузере это ничего не меняет, а в
тестах (Node) относительные адреса не принимаются. 401 ведёт на вход только на защищённых страницах
(`src/shared/routing.ts`: `/campaigns…`, `/settings`).

### 10. `data-testid`

**Решение:** у каждого интерактивного элемента и у корня каждого экрана есть `data-testid`: экраны —
`page-…` (`page-expedition-new`), элементы — `<экран>-<элемент>` (`menu-expedition`). E2E-тесты ищут
элементы только по ним.

### 11. Dev-сервер Vite в окружении агента

**Решение:** по умолчанию Vite слушает `localhost`. В окружении, где работает агент, он оказался
недоступен, поэтому `.claude/launch.json` запускает его с `--host 127.0.0.1`. В `vite.config.ts` адрес
не меняется: в обычном браузере на машине разработчика `localhost` работает.

## Задача 1.5: Полный стек в Docker и каркас E2E (27.09.2026)

### 12. Проверка здоровья бэкенда в Docker

**Решение:** в образ бэкенда добавлен `curl`; healthcheck `docker-compose.yml` опрашивает
`/api/actuator/health`. `web` (Caddy) стартует только после того, как бэкенд стал `healthy`.

### 13. Переменные окружения полного стека

**Решение:** `docker-compose.yml` передаёт бэкенду `DB_URL`, `DB_USER`, `DB_PASSWORD`, собранные из
`POSTGRES_*`, и остальные переменные `.env` без изменений. Отсутствие `POSTGRES_PASSWORD` останавливает
запуск с понятной ошибкой. Порт PostgreSQL наружу не открыт.

### 14. Проект E2E

**Решение:** `web/e2e` повторяет устройство `test/`: Poetry (виртуальное окружение в папке проекта,
`poetry.toml`), `config.json` с адресами сайта и Mailpit, Page Object (`pages/`), скриншот в Allure при
падении. Вместо Appium — Playwright (`pytest-playwright`), браузер — Chromium с размером экрана телефона.
Коды входа читает `support/mailpit.py` через HTTP API Mailpit.

### 15. Интеграционные тесты

**Решение:** базовый класс `support/IntegrationTest` поднимает один контейнер `postgres:17-alpine` на весь

## Задача 1.7: Каталог — загрузка, боссы, достижения (27.09.2026)

### 16. Коды боссов и достижений

**Решение:** коды боссов заданы вручную и совпадают с примерами документации (`VIRAXEN`, `TORAMAT`,
`AWAKENED`, `XITEROS` …). Коды достижений — транслитерация канонического названия заглавными буквами
(ё → e, й → y, х → kh, ц → ts, ч → ch, ш → sh, щ → shch, ю → yu, я → ya, ъ и ь опускаются, пробелы → `_`):
«Затишье» → `ZATISHE`, «Эхо водопада» → `EKHO_VODOPADA`, «Копьё драконоборца» → `KOPE_DRAKONOBORTSA`.
После выпуска коды не меняются: на них ссылаются кампании и эффекты.

### 17. Откуда данные

**Решение:** `bosses.yaml` сгенерирован из `seedBosses()` (`app/.../PrimalDatabase.kt`); тест
`BossCatalogTest.matchesAppSeed` сверяет каждую стойку всех 23 боссов с исходником app (если он лежит рядом с
`web/`). `achievements.yaml` — все 23 достижения, которые встречаются в наградах и условиях
`TaskInfoSeed.kt` и `ChapterInfoSeed.kt`, в каноническом написании (42.1). У Коровона стойка II не только без
прочности, но и со сменой по запросу: в seed app у неё `hsc = NULL`.

### 18. `~` в YAML

**Решение:** Jackson 3 читает YAML по схеме YAML 1.2, где `~` — строка, а не `null`. Загрузчик
(`CatalogLoader.isEmpty`) считает пустым значением отсутствие поля, `null` и `~`.

### 19. Каталог в памяти и в БД

**Решение:** `CatalogLoader` — единственный читатель YAML. Миграция `R__Catalog` пишет каталог в таблицы
(для внешних ключей кампаний), а `CatalogService` держит тот же каталог в памяти. JPA-сущности для таблиц
каталога не нужны. Удалённые из YAML записи миграция не удаляет: на них могут ссылаться кампании.
Контрольная сумма (SHA-256 файлов) служит ETag API и признаком перезапуска repeatable-миграции.

## Задача 1.8: Каталог — задания, главы и язык эффектов (27.09.2026)

### 20. Разбор эффектов

**Решение:** типы эффектов (`rules/effects`) — sealed-интерфейсы и records без аннотаций Jackson: модуль
`rules` зависит только от JDK (ArchUnit). YAML разбирает `catalog/EffectParser` по имени ключа — то же, что
Jackson `DEDUCTION`, но без аннотаций в `rules`. Неизвестный ключ, лишний ключ, стихия в `resources` задания
(стихии даёт общее правило победы) — ошибка загрузки с указанием места. После разбора `CatalogIntegrity`
проверяет, что все задания, достижения и боссы, на которые есть ссылки, существуют, а главы идут 1–11.

### 21. Перенос данных

**Решение:** `quests.yaml` и `chapters.yaml` сгенерированы из `TaskInfoSeed.kt` и `ChapterInfoSeed.kt` app
(там уже учтены исправления C-5…C-10). Тесты `QuestCatalogTest.Parity` и `ChapterCatalogTest.Parity`
сверяют с исходниками app безусловные награды, открываемые задания, достижения, карты наград, особые
награды, цели условий, кузню, лабораторию, набор охотника, решения и истечения. Особая награда задания 33
(«Каждый охотник получает 2 карты крови изначального») — эффект `message`. Сообщение главы 11 сохранено
рядом с `expireAllQuests` и `finalBattle: AWAKENED`.

### 22. Задание 25

**Решение:** в app два условия с правилом «первого совпадения»: «достижение И глава 8 → 34» и
«достижение → 27». В языке эффектов это одно вложенное условие: если есть «Горящий уголёк», то в главе 8 —
задание 34, иначе 27. Поведение то же, формулировка другая: «Если есть достижение «Горящий уголёк»: если
текущая глава 8, то добавить задание 34, иначе добавить задание 27».

### 23. Дополнения в каталоге

**Решение:** дополнение задания — дополнение его босса (Перо, Яд, Лёд); открытие такого задания в главе
помечается тем же дополнением (`{ openQuest: 36, expansion: FEATHER }`). У Тараска, Зеката и Зекалита
дополнение не указано: их стихии — базовые. В первой версии пометки на расчёт не влияют.

## Задача 2.1: Движок боя на TypeScript (27.09.2026)

### 24. Результат команды

**Решение:** `applyCommand` возвращает `{ ok: true, state, events, message }` или
`{ ok: false, state, reason, message }` — отклонённая команда возвращает прежнее состояние, причину
(`RejectionReason`, `battle.md` §3) и текст для экрана. `canApply(state, command)` использует ту же проверку —
по ней интерфейс включает и выключает кнопки. В задаче 2.2 история отмены получает снимок только для
принятых команд.

### 25. Проверка значений

**Решение:** движок сам проверяет числа команд и параметры нового боя: урон и изменение ярости — целые, не 0;
прочность за охотника — целое больше 0 или `null`; порог смены стойки — 1–9; здоровье — 1–10; охотники —
целое больше 0 (D-12). Прочность 0 в `app` зациклила бы подсчёт ран. `validateNewBattle` отдаёт текст
ошибки для полей подготовки (задача 2.3), `createBattle` при ошибке бросает `RangeError`.

### 26. Отличия от `app`

**Решение:** поведение боя — как в `app`, кроме мелочей, которые там выглядели случайными:
- «Закончить раунд» с отрицательным введённым уроном уменьшает накопленный урон, как «OK»; `app` такой ввод
  молча отбрасывал.
- Сообщение конца раунда содержит результат урона: «Нанесено ран: 3. Монстр перешёл на стойку 2! Раунд 2.
  Ярость: 8».
- Сообщение подтверждения стойки называет подтверждённую стойку, затем результат перенесённого урона:
  «Стойка 2. Урон для раны: 2, смена: 7 HP. Нанесено ран: 2. Монстр перешёл на стойку 3!». При победе —
  только «Монстр побеждён! Нанесено ран: N».
- Выплеск ярости — только при росте ярости до 3 за охотника (в `app` окно открывалось и при +0).
  Изменение ярости на 0 отклоняется.
- Победа и поражение закрывают оба окна (`pendingStance`, `rageSurgePending`).

Оставлено как в `app`: «Затвердевший» сжигает остаток и на смене стойки — на новую стойку переносится 0.

### 27. Границы `src/domain`

**Решение:** кроме правил ESLint (qa 8), тест `src/domain/domain-imports.test.ts` читает исходники
`src/domain` (`import.meta.glob` с `?raw`) и проверяет, что импорты не выходят за папку: пакеты и файлы
остального приложения запрещены.

## Задача 2.2: Отмена и хранение боя в браузере (27.09.2026)

### 28. Что попадает в историю отмены

**Решение:** снимок кладёт `perform` (`history.ts`) только для принятой команды — отклонённая (например,
«Заживить рану» при здоровье 10) стек не меняет, как в `app`. Отменяются все команды, включая статусы,
подтверждение стойки и выплеск ярости (`battle.md` §6). Отмена недоступна, если результат кампании уже
отправлен (`submission.status = SENT`).

### 29. Где живут операции над записью боя

**Решение:** к файлам плана добавлен `src/domain/battle/localBattle.ts`: `createLocalBattle` (новая запись
для экспедиции и кампании — её вызовут экраны подготовки 2.3 и 5.4) и `isUnfinished` (кнопка «Вернуться к
бою», подтверждение замены боя). Тексты описаний команд — в `messages.ts` (`describeCommand`).

### 30. Проверка сохранённой записи

**Решение:** `parseStoredBattle` проверяет запись полностью — типы и диапазоны всех полей состояния,
стоек и снимков истории. Бой из хранилища сразу идёт в движок, а запись могли испортить расширения,
ручная правка или старый код. Отброшенная запись удаляется, чтобы предупреждение не повторялось. Перевод
форматов — цепочка функций `MIGRATIONS[N]: N → N + 1`; пока формат один, список пуст, механизм проверяется
тестом с подставленным переводом.

### 31. Текущий бой для экранов

**Решение:** `useActiveBattle` читает общий для вкладки объект `ActiveBattle` через
`useSyncExternalStore`: подготовка создаёт бой, экран боя выполняет команды, главное меню показывает
«Вернуться к бою» — все видят одно состояние. По умолчанию объект работает с `window.localStorage`; тесты
подставляют свой через `ActiveBattleContext`. Подтверждение замены незаконченного боя показывает экран
(`hasUnfinished`, текст `ru.battle.replaceUnfinished`), `start` заменяет бой без вопросов.

## Задача 2.3: Фронтенд: подготовка экспедиции (27.09.2026)

### 32. Список боссов

**Решение:** порядок — `sortOrder` каталога; он совпадает с порядком списка в `app` (стихия по алфавиту,
затем имя, Пробуждённый последним). Подпись как в `app`: «Коралл - Коровон», у Пробуждённого — только имя;
названия стихий — из `GET /catalog/dictionaries`. Список нативный (`NativeSelect`): на телефоне открывается
системный выбор; иконка стихии выбранного босса — слева в поле. Каталог не загрузился — сообщение с
«Повторить», ручной ввод работает.

### 33. Контракт OpenAPI для генерации клиента

**Решение:** springdoc по умолчанию делал все поля необязательными, без `null`, с типом ответа `*/*` и
тегом `catalog-controller` — сгенерированные типы заставляли бы проверять каждое поле. Теперь
(`common/api/OpenApiConfig`, только когда springdoc включён — профиль `dev`) все поля схем обязательны:
Jackson пишет все поля записей, включая `null`. `null` разрешён только полям с `@ApiNullable` (OpenAPI 3.1:
`type: [string, null]`, для ссылок — `oneOf` со схемой `null`). Ответы — `application/json`, контроллер
каталога — тег `catalog`. Клиент (`src/api/generated`) хранится в git; контракт проверяет
`OpenApiContractIT`. Для тел запросов с необязательными полями правило дополним, когда такие запросы
появятся (задача 3.1).

### 34. Уровень враждебности

**Решение:** уровни, для которых у выбранного босса нет стоек, недоступны (у Пробуждённого — только 3). В
`app` их можно было выбрать, но поля при этом не менялись — это сбивало с толку. При выборе босса без
текущего уровня берётся первый доступный.

### 35. Поля стойки

**Решение:** вместо «пусто = по запросу» у порога смены стойки — переключатель «По здоровью / По запросу /
Последняя» (модель боя различает три режима, `battle.md` §2) и поле здоровья для режима «По здоровью».
Пустая прочность — стойка без порога раны, как в `app`. Ручной ввод — значения `app`: прочность 4 за
охотника, смена при 7; при возврате к ручному вводу они восстанавливаются. Поля и их разбор
(`StanceFields`, `stanceForm`) и работа с каталогом боссов (`bossCatalog`) лежат в `features/battle`: их же
использует окно «Смена стойки!» (2.4) и подготовка боя кампании (5.4).

### 36. Тесты экранов

**Решение:** MSW по умолчанию отвечает каталогом — фрагментом настоящего (`src/test/fixtures/catalog.ts`:
Коровон, Вираксен, Пробуждённый). `renderRoutes` даёт каждому тесту свой текущий бой в памяти, а не общий
`localStorage`.

## Задача 2.4: Фронтенд: экран боя (27.09.2026)

### 37. Отличия экрана от `app`

**Решение:** поведение и тексты — как в `app`, отличия описаны в `battle.md` §8.1: сообщение под
информационной панелью (внизу экрана телефона его не видно), описание отменяемого действия, «±» для
отрицательного урона, «Ожидание… N урона» в строке заголовка (кнопки +N не сдвигаются под пальцем — это
нашлось при проверке в браузере), фокус на «OK» в окне смены стойки, отмена итога на экранах победы и
поражения.

### 38. Окно «Смена стойки!» без данных каталога

**Решение:** поля пустые, режим — «По запросу»: в `app` пустой порог означал «по запросу», и сценарий
мобильного UI-теста (указать только прочность и нажать OK) проходит так же. Поле «Здоровье босса в новой
стойке» видно всегда, пустое — здоровье не меняется.

### 39. Подсветка и вибрация по результату команды

**Решение:** подсветку и вибрацию запускает обработчик команды, а не эффект, следящий за состоянием:
`highlight(before, after)` после каждой команды и отмены, вибрация — по событиям команды (`vibrationFor`).
Так же сделано в `app` (`highlightChanged(before)`). Таймер кнопок +N срабатывает позже рендера, поэтому
состояние «до» берётся из `getBattle()` на момент вызова.

### 40. «Выход в меню»

**Решение:** во время боя бой сохраняется, в меню появляется «Вернуться к бою». С экранов победы и
поражения «Выход в меню» и «Новый бой» удаляют бой, как `resetBattle` в `app`. Бой кампании (задача 5.4)
получит свой экран итога.

### 41. E2E-сценарии мобильного приложения

**Решение:** сценарии `test/battle_tests` перенесены в `web/e2e/tests/test_expedition.py` с теми же
названиями и проверками (Page Object — `pages/expedition_page.py`, `pages/battle_page.py`). Переключатели
Mantine прячут поле под дорожкой — Page Object нажимает на дорожку (`click(force=True)`). Окна открываются с
анимацией, поэтому «закрыть выплеск, если он появился» ждёт окно до 1 секунды.

## Задача 3.1: Вход по коду из письма (27.09.2026)

### 42. Письмо и медленный DNS

**Решение:** JavaMail строит `Message-ID` и приветствие EHLO из имени машины (`InetAddress.getLocalHost()`),
а разрешение имени может занимать секунды (так было на машине разработчика: письма в тестах «опаздывали»).
`MailConfig` задаёт `mail.from` (адрес из `MAIL_FROM`) и `mail.smtp.localhost` (хост из `PUBLIC_URL`) —
к DNS JavaMail не обращается, а EHLO называет домен сайта. Настройки SMTP — `primal.mail.*` из `SMTP_*`,
`SMTP_TLS` → `NONE`/`STARTTLS`/`SSL`.

### 43. Неверный код и транзакция

**Решение:** `verify` — `@Transactional(noRollbackFor = ApiException.class)`: уменьшение числа попыток
сохраняется, хотя ответ — ошибка `INVALID_CODE`. Строка запроса кода блокируется (`PESSIMISTIC_WRITE`) —
параллельные попытки не обходят счётчик. После 5 неверных попыток ответ — `CODE_EXPIRED`; запрос с
несуществующим `challengeId` — тоже `CODE_EXPIRED`, чтобы не отличать его от устаревшего.

### 44. Устройство при входе

**Решение:** если браузер пришёл с cookie гостевого устройства (ссылка-приглашение, этап 6), устройство
привязывается к аккаунту, токен не меняется; перенос доступов гостя на аккаунт — в задаче 6.1. Если в
браузере был вход другим (или тем же) аккаунтом, прежнее устройство отзывается и выдаётся новое. Cookie
`PRIMAL_DEVICE` действует только для `/api` — страницам сайта она не нужна.

### 45. Время и тесты

**Решение:** сервисы берут время из `Clock` (`TimeConfig`); в интеграционных тестах его заменяет
`MutableClock` — так проверяется срок кода (10 минут), а в задаче 3.2 — продление cookie и простой
устройства. Письма в тестах перехватывает `MailCapture` (главный `JavaMailSender` контекста); код тесты
берут из письма, как пользователь. `AuthHelper.login(email)` — вход для тестов следующих задач.
Счётчики частоты, часы и письма сбрасываются перед каждым тестом (`IntegrationTest`).

## Задача 3.2: Устройства и аутентификация запросов (27.09.2026)

### 46. Когда продлевать cookie

**Решение:** в `device` добавлено поле `cookie_renewed_at` (миграция `V2`): без него неизвестно, когда
cookie выдавалась последний раз. Продление — тем же токеном, с новым `Max-Age` 400 дней. Визит
(`last_seen_at`) пишется в БД не чаще раза в час; устройство без визитов больше 365 дней не принимается.

### 47. Кэш устройств

**Решение:** найденное по хешу токена устройство кэшируется (Caffeine, 60 секунд, до 10 000 записей);
неизвестные токены не кэшируются, чтобы перебор не заполнял кэш. Отзыв, «Выйти», «выйти на других» и
привязка гостевого устройства к аккаунту сразу удаляют устройство из кэша этого экземпляра; на остальных
экземплярах — не позже чем через минуту (`architecture.md` §6).

### 48. CSRF для SPA

**Решение:** `csrf.spa()` Spring Security 7: cookie `XSRF-TOKEN` (не HttpOnly) и сравнение с заголовком
`X-XSRF-TOKEN`. Первый изменяющий запрос браузера может прийти раньше любого другого (запрос кода входа),
поэтому есть `GET /api/v1/auth/csrf` → 204: его вызывает `apiFetch`, если cookie ещё нет. Swagger UI в
профиле `dev` передаёт заголовок сам (`springdoc.swagger-ui.csrf.enabled`). В тестах вместо `csrf()` из
spring-security-test — `support/Xsrf.xsrf()`: ставит cookie и заголовок, как браузер (помощник
spring-security-test с режимом `spa()` не согласуется). Отказ CSRF — `403 FORBIDDEN` в формате problem+json.

### 49. Ошибки безопасности и публичные пути

**Решение:** 401 и 403 фильтров Spring Security отдаются в том же формате problem+json, что и ошибки
контроллеров (`Problems.of`). Без входа доступны `/api/v1/auth/code/**`, `/api/v1/auth/csrf`,
`/api/v1/share/**`, `/api/v1/catalog/**`, `/api/actuator/health`, описание API (включено только в `dev`).
`/auth/me` без входа — `401`: так фронтенд узнаёт, что входа нет.

### 50. Ответ «Кто я»

**Решение:** у обоих видов ответа одинаковые поля: `kind`, `user` (у гостя `null`), `device` с `id` и
`displayName` (у пользователя `null`) — сгенерированный клиент получает один тип без объединений. Пустое
имя в `PATCH /auth/me` сбрасывает его.

## Задача 3.3: Фронтенд: вход и настройки (28.09.2026)

### 51. Поле кода и повторная отправка

**Решение:** шесть ячеек — `PinInput` Mantine: цифровая клавиатура, `autocomplete="one-time-code"`,
вставка кода целиком; код отправляется сам после 6-й цифры (кнопка «Войти» — на случай ручного ввода).
Отсчёт до повторной отправки берётся из `resendAfter`, но не дольше минуты: часы браузера могут не
совпадать с серверными. Если сервер всё же ответил `429`, отсчёт идёт по `retryAfter`. После
`CODE_EXPIRED` новый код можно запросить сразу.

### 52. Защита экранов

**Решение:** `RequireAuth` оборачивает кампании и настройки: `useMe` запрашивает `GET /auth/me`, ответ
`401` означает «входа нет» (не ошибка), и экран ведёт на `/login?next=…`. Пускают и пользователя, и гостя
по ссылке (гостю нужны кампании, этап 6). Если устройство отозвали посреди работы, любой ответ `401` на
защищённой странице сбрасывает «кто я» и открывает вход (`Layout`). Адрес возврата `next` принимается
только внутри сайта (`safeNext`). В тестах MSW по умолчанию отвечает на `/auth/me` кодом `401`, вход
подставляет `signedIn()`.

### 53. Главное меню

**Решение:** «Кампании» видны всегда и без входа ведут на вход; внизу — «Войти» или имя и «Настройки».
Имя по умолчанию — часть почты до «@», у гостя — «Гость».

### 54. Лимиты по IP в E2E

**Решение:** все E2E-тесты входят с одного IP, а лимит — 20 писем в час; уже третий прогон подряд получил
бы `429`. Лимиты по IP стали настройками (`PRIMAL_CODES_PER_IP_HOUR`, `PRIMAL_VERIFICATIONS_PER_IP_HOUR`,
по умолчанию 20 и 60); в `.env.example` для локального стека они подняты, на сервере их не задают.
Лимит на адрес почты (1 в минуту, 5 в час) не настраивается: повторный вход тем же адресом в течение
минуты E2E проверяет как сообщение «Слишком много попыток. Повторите через N с.».

### 55. Имена операций API

**Решение:** у операций входа заданы `operationId` (`getMe`, `listDevices`, `revokeDevice` …), а параметр
`CsrfToken` скрыт из описания: иначе orval генерировал хуки `useList`, `useMe` и лишний параметр запроса.

## Задачи 4.1–4.2: Кампании и лист кампании (28.09.2026)

### 56. Необязательные поля запросов

**Решение:** правило «все поля обязательны» (решение 33) не подходит для `PATCH`: поле, которое не меняется,
не передаётся. Такие поля помечаются `@ApiOptional` — в контракте они не входят в `required`, и orval делает
их необязательными (`name?: string`). Версия (`expectedVersion`) обязательна.

### 57. Версия кампании

**Решение:** `campaign.version` — `@Version` JPA. Сервисы вызывают `touch()` при любом изменении кампании,
в том числе охотников, навыков, ресурсов, заданий и достижений: меняется `updated_at`, и JPA увеличивает
версию. Устаревший `expectedVersion` — `409 VERSION_CONFLICT` с актуальным листом в `current`; если
конфликт обнаружила сама БД (две записи одновременно), — `409` без `current`.

### 58. Доступ к кампании

**Решение:** `AccessService` (модуль `access`) читает владельца кампании SQL-запросом, а не через
репозиторий модуля `campaign`: ArchUnit запрещает чужие репозитории, а зависимость `access → campaign`
создала бы цикл. Нет доступа или нет кампании — `404`. Доступ по ссылке (`LINK`) и `403 OWNER_ONLY` для
гостя — в задаче 6.1.

### 59. Сущности кампании

**Решение:** дочерние сущности хранят `campaign_id`/`hunter_id` числом, без связей JPA: удаление кампании
убирает всё каскадом в БД (`on delete cascade`), а лист строится несколькими простыми запросами (охотники,
навыки, ресурсы, задания, достижения, трофеи). `char(1)` ветви навыка — `@JdbcTypeCode(CHAR)`, `smallint` —
`short`: схему проверяет `ddl-auto: validate`. Правило доступных ступеней — `rules/model/SkillTree`
(перенос `SkillValidatorImpl`).

### 60. Имя владельца и порядок отряда

**Решение:** имя владельца — имя аккаунта или часть почты до «@» (`AccountService.userName`). Порядок
охотников в запросе создания — порядок в отряде (`position`); на экране создания это порядок выбора
классов. Пятый выбранный класс блокирует остальные; снятие выбора снова их открывает.

### 61. E2E и компоненты Mantine

**Решение:** у `Chip` поле выбора скрыто — Page Object нажимает на подпись `label[for=…]`; у `Badge`
текст в верхнем регистре через CSS — проверяется `text_content()`, а не `inner_text()`.

## Задача 4.3: Навыки и ресурсы охотников (28.09.2026)

### 62. Один сервис охотника

**Решение:** вместо `SkillService` и `ResourceService` — один `HunterService` (имя игрока, навыки, ресурсы):
у всех трёх операций общая проверка доступа и охотника, и все увеличивают версию кампании. Правила
ступеней — `rules/model/SkillTree` (тест `SkillTreeTest`; отдельных тестов `SkillValidatorImpl` в `app` нет).
Операции над охотником не требуют `expectedVersion`: это приращения, а не перезапись.

### 63. Списание ресурсов

**Решение:** «всё или ничего»: сначала проверяются все изменения по текущим количествам (понятное
сообщение «Не хватает ресурсов: Огонь.»), затем начисление — upsert, списание — `update … quantity -
:amount`. Upsert с отрицательным количеством не годится: PostgreSQL проверяет CHECK у вставляемой строки ещё
до `on conflict`. Если параллельный запрос успел списать ресурс, CHECK не даёт уйти в минус, транзакция
откатывается целиком — `422 NOT_ENOUGH_RESOURCES`. Нативные запросы очищают контекст JPA
(`clearAutomatically`), иначе ответ показал бы старые количества.

## Задача 4.4: Планировщик эффектов (28.09.2026)

### 64. Текст результата правила

**Решение:** результат зависит от вида правила, который определяется по его действиям: открывает
задание — «Добавлено задание N.», иначе «Достижения нет, задание не добавляется.» (у задания, если условие —
«есть достижение») или «Условие не выполнено, задание не добавляется.» (так же отвечает `app` для глав);
выдаёт достижение — «Достижение есть, добавлено достижение «X».», «Достижение «X» уже получено.» или
«Достижения нет.»; улучшение набора и сообщение — «Достижение есть, улучшите набор охотника.»,
«Достижение есть: <сообщение>.» или «Достижения нет.». Результат «Не применяется: уже добавлено
задание N.» не нужен: задание 25 — одно вложенное правило (решение 22).

### 65. Снимок и вложенные условия

**Решение:** все условия набора, включая вложенные, вычисляются по одному снимку (`CampaignFacts`:
коды достижений, глава, открытые и выполненные задания). Достижение или задание, которые выдаёт тот же
набор, на его условия не влияют — это проверяют тесты. Пометка `expansion` на расчёт не влияет.
Планировщик собирает `CatalogService.planner()` — с названиями достижений из каталога.

### 66. Применение плана

**Решение:** `PlanApplier` выполняет план в транзакции вызывающего сервиса: ресурсы — каждому охотнику;
новое или истёкшее задание — открыто (глава открытия — текущая), открытое и выполненное не меняются;
истекают только открытые; достижение — без дублей ни по коду, ни по нормализованному названию (ручная
запись «голос  волтьяра» считается уже полученным «Голосом Волтьяра»); кузня и лаборатория не выше 3;
финальный бой задаёт `final_boss_code`. Сообщения, карты наград и улучшение набора возвращаются списком
инструкций для экрана наград. Версия кампании растёт.

### 67. Ресурсы и контекст JPA

**Решение:** текущие количества ресурсов читаются проекцией (`HunterResourceRepository.quantities`), без
загрузки сущностей: иначе после нативного начисления в той же транзакции JPA вернул бы устаревшие
сущности. Очистку контекста (`clearAutomatically`, решение 63) убрали: она отсоединяла бы кампанию посреди
применения плана.

## Задача 4.5: Задания и достижения кампании (28.09.2026)

### 68. «Выполнено» и пояснения

**Решение:** задание должно быть открыто (`422 QUEST_NOT_OPEN`). План наград победы строится по снимку
до выполнения, применяются только открытия заданий (`Plan.only(OpenQuest)`), а в ответ попадают пояснения
только тех правил, что открывают задания (`EffectPlanner.opensQuests`): правило условного достижения при
ручном «Выполнено» ничего не делает, и показывать его результат было бы неверно.

### 69. «Отмена» и редактор

**Решение:** «Отмена» — только у выполненного задания; для остальных добавлен код
`422 QUEST_NOT_COMPLETED`. Редактор открытых заданий не открывает заново истёкшие задания из списка (в `app`
открывал): `api.md` §5.5 обещает не трогать выполненные и истёкшие (D-5). Задание вне каталога — `400`.

### 70. Достижения вручную

**Решение:** введённое название обрезается и схлопывает пробелы; если оно совпадает с достижением
каталога (регистр, ё/е, пробелы), сохраняется каноническое название и код. Равнозначное достижение
кампании — то же нормализованное название или тот же код — удаляется и заменяется новым, как в `app`: одно
и то же достижение второй раз не появляется, а своё достижение в другом написании заменяет прежнее.

## Задача 4.6: Лист кампании (28.09.2026)

### 71. Версия в кэше листа

**Вопрос:** правки главы и заметок передают `expectedVersion`, а ресурсы, навыки, задания и достижения —
нет, хотя тоже растят версию. Как не получать ложный `409` после них?

**Решение:** после успешного изменения клиент сам увеличивает `version` в кэше листа на 1 (`api.md` §5.3
обещает рост на 1 при любом изменении), а `expectedVersion` берёт из кэша в момент отправки. Ответы,
описывающие изменение полностью (навык, ресурсы, «Отмена», редактор заданий, удаление достижения),
применяются без перезапроса; «Выполнено» и добавление достижения ещё и перезапрашивают лист.

### 72. Ресурсы пачками

**Решение:** нажатия +/− копятся 400 мс и уходят одним запросом `adjust`; следующая пачка ждёт ответа на
предыдущую. Так быстрые нажатия не порождают гонку запросов, а отказ «всё или ничего» (`422`) откатывает
всю пачку: значения берутся с сервера, причина — в уведомлении. Значение на экране меняется сразу, не
дожидаясь сервера, — как в `app`, где «+» срабатывает мгновенно.

### 73. Заметки: автосохранение и конфликт

**Решение:** кнопки «Сохранить» нет — заметки сохраняются через 800 мс после изменения, при потере фокуса и
при уходе со страницы. Если `409` вызван правкой другой части кампании (в `current` те же заметки, от
которых начат черновик), запрос молча повторяется с новой версией. Если заметки изменили на другом
устройстве — уведомление «Состояние обновилось», черновик остаётся в поле и сохранится при следующем
изменении (побеждает последняя правка, но пользователь предупреждён).

### 74. Редактор заданий показывает все задания

**Решение:** в редакторе все 49 заданий каталога, включая задания дополнений (36 — «Перо»): так в `app`, и
сценарий 3.17 отмечает задание 36. Выбора дополнений в v1 нет, поэтому скрывать их задания было бы
потерей возможности, а не упрощением. Стихии дополнений в ресурсах тоже показываются (9 стихий, как в
`app`).

### 75. Открытый навык, который нельзя снять

**Решение:** ступень 1 при открытой ступени 2 не снимается (`SkillTree.canLock`). Кнопка не получает
`disabled` — иначе она выглядела бы серой, как закрытая, — а только `aria-disabled` и не реагирует на
нажатие. Закрытая недоступная ступень 2 — `disabled`.

### 76. Mantine в тестах

**Решение:** тесты рендерят `MantineProvider env="test"` — без анимаций и порталов, иначе подсказки
`Autocomplete` не успевали появиться. Уведомления Mantine живут в общем хранилище модуля, поэтому
`setup.ts` очищает их после каждого теста; `document.fonts`, которого нет в jsdom, подменяется для
`Textarea autosize`.

## Задача 5.1: Подготовка и отметки о начале боя (28.09.2026)

### 77. Лист кампании и бои без цикла модулей

**Решение:** отметки хранит `progression`, а показывает и лист кампании (`activeBattles`, `recentBattles`).
Чтобы `campaign` не зависел от `progression`, лист получает бои через интерфейс `campaign.CampaignBattles`;
реализация — `progression.CampaignBattleQueries`. Боссы и задания в виде листа строит общий
`campaign.CampaignViews`.

### 78. Выбор босса в прологе и финале

**Решение:** `forcedBoss` заполняется не только в главе 11, но и в прологе: бой пролога — всегда с
Вираксеном, награды пролога (трофей Вираксена и 2 «Огня», §7.2) от выбора не зависят. Задание в прологе —
`422 QUEST_NOT_OPEN` («заданий нет»), в главе 11 — `422 FINAL_BOSS_REQUIRED`. Отметка о начале финального
боя с другим боссом — тоже `FINAL_BOSS_REQUIRED`: проверка «только этот босс» из плана.

### 79. Пройденная кампания

**Решение:** подготовка и старт боя в пройденной кампании (`COMPLETED`) — `409 CAMPAIGN_CHANGED`
«Кампания пройдена»: результат такого боя всё равно не был бы принят (§7.3), поэтому предупреждаем заранее.

### 80. Повтор отметки и гонка

**Решение:** повтор с тем же `id` возвращает существующую запись без проверок — кампания могла измениться,
а бой уже идёт. Два одновременных одинаковых запроса не падают на первичном ключе: вставка идёт через
`insert … on conflict (id) do nothing`, затем запись читается. Идентификатор боя чужой кампании — `404`.

### 81. Время и автор отметки

**Решение:** `startedAt` — от браузера (бой мог начаться без сети, отметка придёт позже), но не позже
времени сервера, иначе отметка «из будущего» не устаревала бы. Автор — устройство запроса: пользователь
показывается по имени аккаунта, гость — по имени устройства или «Гость», удалённое устройство — «—».

### 82. Отметка не меняет версию кампании

**Решение:** старт и снятие отметки не увеличивают `version`: отметка — предупреждение, а не состояние
кампании. Иначе чужой старт боя давал бы ложный `409` при правке главы или заметок.

## Задача 5.2: Результат боя (28.09.2026)

### 83. Кто применяет итог

**Решение:** расчёт наград (общие правила, план задания, `overrides`) — в `progression.BattleResultService`,
изменение кампании — в `campaign.BattleOutcomes`: трофей, выполненное задание, закрытие главы или кампании и
план через `PlanApplier`. Модуль `progression` не трогает сущности и репозитории `campaign`.

### 84. Одна победа на главу

**Решение:** «Принять» блокирует строку кампании (`select … for update`) до конца транзакции и только потом
проверяет `progressSeq`. Две победы одной главы, отправленные одновременно, проверяются по очереди: вторая
видит выросший `progressSeq` и получает `409 CAMPAIGN_CHANGED`. Оптимистичная блокировка по `version` дала
бы `409 VERSION_CONFLICT` без понятной причины.

### 85. Причина отказа без склонений и часовых поясов

**Решение:** причина называет босса в кавычках («в бою с боссом «Торамат»») и автора через «результат от:»
— без склонения имён и глаголов по роду. Время закрывшей победы сервер в текст не пишет (он не знает часовой
пояс игроков) — оно передаётся полем `closedBy.submittedAt`, экран покажет его по местному времени.

### 86. Бой без задания без босса

**Решение:** превью показывается (без трофея и стихий), а «Принять» отказывает `422 BOSS_REQUIRED` с
текстом из `app` — «Босс не выбран — укажите его через «Редактировать»». С `overrides` босс обязателен для
победы любого вида: трофей без босса не записать.

### 87. Что показывает превью

**Решение:** уже добавленные задания и уже полученные достижения в превью не повторяются — окно показывает,
что изменится. Применение безопасно и без этого фильтра (повторы — no-op, решение 66). Превью боя, итог
которого уже сохранён, — `409`: повтор «Принять» при этом возвращает сохранённый итог (однократность).

### 88. Итог без отметки о начале

**Решение:** запись боя создаётся из полей результата (автор старта — отправитель). Если отметка есть, её
поля старта обновляются полями результата: они повторяют отметку, а `purpose` выводится из снимка, поэтому
запись всегда согласована с проверкой БД «`QUEST` ⇔ `quest_number`».

## Задача 5.3: Переход главы (28.09.2026)

### 89. Ответы на решения в адресе превью

**Решение:** вместо `decision.<CODE>=<OPTION>` — повторяемый параметр `decision=<CODE>:<OPTION>`. Такой
параметр OpenAPI описывает как массив строк, и сгенерированный клиент передаёт его без ручной сборки адреса;
произвольные имена параметров (`decision.*`) в OpenAPI не описать.

### 90. Порядок применения перехода

**Решение:** сначала кампания входит в новую главу (`chapter = N`, `ACTIVE`, `progress_seq + 1`), затем
применяются эффекты решений (`source = DECISION`) и главы (`CHAPTER`). Поэтому задания, достижения и
истечение заданий записываются с главой N — как «открыто в главе 7» в листе. Условия решений и главы
вычисляются по снимку до перехода (решение 66, `data-model.md` §4.3).

### 91. Переход под блокировкой и с версией

**Решение:** «Принять» и «Отклонить» блокируют строку кампании и сверяют `expectedVersion` из превью: если
кампанию успели изменить (например, открыли задание по ссылке), список последствий в окне мог устареть —
`409 VERSION_CONFLICT` с актуальным листом, и экран покажет новый список.

### 92. Вид правила в пояснениях

**Решение:** `EffectPlanner.kind` стал публичным: вид пояснения (`QUEST`, `ACHIEVEMENT`, `KIT`, `MESSAGE`)
берётся из условия верхнего уровня, текст — из плана (`RuleViews`). Окна наград группируют правила, как в
`app`: «Условные задания» и «Условные награды».

### 93. Сообщение о пройденной кампании

**Решение:** превью победы в финальном бою добавляет в `rewards.messages` «Кампания пройдена! Пробуждённый
повержен.» (`data-model.md` §4.3). Отдельного окна для этого на сервере нет — текст показывает фронтенд.

## Задача 5.4: Бой кампании, результат, переход главы в браузере (28.09.2026)

### 94. Одинаковые имена схем OpenAPI

**Проблема:** springdoc называет схему по простому имени класса. Новые `Rewards`, `RuleView` и
`DecisionView` совпали с классами каталога и заданий, и схемы склеились: у превью перехода пропал
`selected`, у `Quest.victory` появились поля итога боя.

**Решение:** DTO переименованы (`BattleRewards`, `RewardRule`, `TransitionDecision`, `TransitionOption`),
достижение в наградах — общий `CatalogViews.AchievementRef`. `OpenApiContractIT.uniqueSchemaNames` обходит
тела запросов и ответов всех контроллеров и падает, если у двух разных record одно простое имя.

### 95. Одна форма подготовки для экспедиции и кампании

**Решение:** поля подготовки вынесены в `expedition/BattleSetupForm`; экспедиция и бой кампании отличаются
префиксом `data-testid`, начальными значениями и блокировкой босса (пролог, финал). Стойки боя кампании
берутся из каталога для выбранных босса и сложности — те же, что отдаёт `battle-setup`, но и после смены
босса игроком.

### 96. Экран итога держит бой у себя

**Решение:** экран наград запоминает бой при открытии: успешная отправка удаляет бой из браузера, а экран
ещё переходит дальше или показывает «Кампания пройдена!». Пролог (36.1) отправляется один раз при открытии
экрана без превью.

### 97. «Выход в меню» после боя кампании

**Решение:** в экспедиции «Выход в меню» после итога удаляет бой, как раньше; в кампании — нет: итог ещё не
отправлен, меню и лист показывают «Результат боя не отправлен» (D-13). Удаляет бой только успешная отправка
или замена новым боем (с подтверждением).

### 98. Решение главы учитывается сразу

**Решение:** окно решения закрывается по ответу сразу, не дожидаясь нового превью с `decision=…`: ответ
хранится на экране, а превью перезапрашивается с ним. «Принять» недоступно, пока новое превью не пришло
(`decisionsComplete`).

### 99. После создания кампании — подготовка пролога

**Решение:** создание кампании ведёт на `/campaigns/{id}/battle/new` (`battle.md` §9, п. 9), а не на лист.
E2E листа кампании открывают лист по адресу.

## Задача 6.1: Ссылки-приглашения (28.09.2026)

### 100. Перенос доступов гостя — событием

**Решение:** модуль `access` зависит от `identity` (кто делает запрос), поэтому `identity` не вызывает
`access` напрямую. При входе с гостевого устройства `DeviceService.signIn` публикует `GuestDeviceAttached`, а
`ShareLinkService` в той же транзакции переписывает `share_access` устройства на пользователя (дубликаты
пропускаются `on conflict`, записи устройства удаляются).

### 101. Доступ проверяется запросом к БД

**Решение:** `AccessService.require` — владелец или запись `share_access` пользователя или этого устройства по
действующей ссылке кампании. Отзыв и перевыпуск ссылки закрывают доступ сразу, без кэшей: каждый запрос
проверяет `share_link.revoked_at`.

### 102. Вход по ссылке без cookie

**Решение:** `join` создаёт гостевое устройство (с именем из запроса) и выдаёт его cookie в ответе.
Устройство сохраняется сразу (`saveAndFlush`): запись доступа вставляется следом SQL-запросом и ссылается на
него внешним ключом. Вставка доступа — `on conflict … do nothing`: повтор и гонка двух вкладок не дают
дубликатов и ошибок.

### 103. Владелец и его ссылка

**Решение:** владелец, открывший свою ссылку, ничего не получает (у него и так `OWNER`); ответ тот же — id
кампании, фронтенд просто откроет лист. Управлять ссылкой (создать, посмотреть, отозвать) может только
владелец; участнику по ссылке — `403 OWNER_ONLY`, чужому — `404`.

## Задача 6.2: Обновления в реальном времени (28.09.2026)

### 104. Уведомление после коммита — одно на кампанию

**Решение:** `realtime.ChangeEvents.campaignChanged` регистрирует синхронизацию транзакции: событие уходит
в `afterCommit`, откат ничего не отправляет, а несколько изменений одной кампании в запросе (например,
«Принять» итог: трофей, ресурсы, задания) дают одно событие с итоговой версией. Версия читается из БД после
коммита. Вызывают его `CampaignService.touch/update`, отметки о начале и брошенные бои, итоги боёв.

### 105. Отзыв доступа — события модулей, а не вызовы

**Решение:** `realtime` зависит от `access` и `identity` (права, имя автора), поэтому они не вызывают
`realtime` сами: `ShareLinkService` публикует `ShareLinkChanged`, `DeviceService` — `DevicesRevoked`, а
`EventHub` слушает их после коммита (`@TransactionalEventListener`) и перепроверяет права подписчиков.
Кампания и прогрессия вызывают `ChangeEvents` напрямую — `realtime` от них не зависит.

### 106. Подписчики в памяти

**Решение:** реестр потоков — в памяти одного экземпляра бэкенда (`architecture.md` §8). Поток без
таймаута, пульс `:ping` каждые 25 секунд; ошибка отправки убирает поток. Первая строка `:connected`
уходит сразу: прокси и браузер видят, что поток открыт. Проверено через Caddy: событие приходит за ~0,2 с
после правки на другом устройстве.

## Задача 6.3: Фронтенд совместной игры (28.09.2026)

### 107. Отметка о начале боя не меняет версию — признак `battles`

**Проблема:** клиент пропускает события с версией «не новее своей», чтобы не перезапрашивать лист после
собственных правок. Но отметка о начале боя версию не меняет (решение 82) — баннер «Идёт бой» у владельца
не появлялся (E2E совместной игры).

**Решение:** в `campaign.updated` добавлен `battles`: `ChangeEvents.battlesChanged` вызывают отметки о
начале, брошенные бои и итоги боёв. С `battles = true` клиент перезапрашивает запросы кампании всегда.

### 108. Живые обновления — перезапрос, а не данные

**Решение:** `useLiveUpdates` на листе кампании открывает `EventSource` и при событии инвалидирует все запросы
кампании (ключи orval начинаются с `/api/v1/campaigns/{id}`: лист, подготовка боя, история, переход главы) и
список кампаний. `access.revoked` — поток закрывается, данные кампании удаляются из кэша, сообщение и
возврат в меню. В jsdom `EventSource` нет — тесты подставляют свой источник.

### 109. Вход по ссылке

**Решение:** `/s/:token` показывает приглашение, гостю — поле имени (для истории боёв), вошедшему — только
«Присоединиться»; после `join` адрес заменяется на лист кампании (`navigate(…, { replace: true })`), и токен не
остаётся в истории браузера. «Кто я» перезапрашивается: гость без cookie получил устройство.

### 110. «Поделиться» и история боёв

**Решение:** окно «Поделиться» — только у владельца: ссылка с «Копировать» (Mantine `CopyButton`), QR-код
(`qrcode`, картинка data URL), список присоединившихся, «Перевыпустить» и «Отозвать» с подтверждением прямо
в окне. История боёв — вкладка «История» листа: итог, задание, глава, кто начал и кто отправил итог, статус.

## Задача 7.1: PWA и экспедиция без сети (28.09.2026)

### 111. Иконки приложения

**Решение:** самая крупная иконка `app` — 156×156 (`mipmap-xxxhdpi`), а для установки нужны 192 и 512.
Иконки сайта (`public/icons`) получены из неё масштабированием (Lanczos): `icon-192`, `icon-512`,
`maskable-512` (картинка в безопасной зоне 80 % на фоне темы), `apple-touch-icon` (180) и `favicon-48`. При
появлении исходника большего размера их стоит пересоздать.

### 112. Что кэширует service worker

**Решение:** `vite-plugin-pwa` (generateSW, `autoUpdate`): статика сайта — заранее (precache), справочники
`/api/v1/catalog/bosses` и `/dictionaries` — «stale-while-revalidate», остальные запросы `/api` не
кэшируются и без сети падают (навигационный откат на `index.html` для `/api/*` отключён). Caddy отдаёт
`sw.js` и манифест с `Cache-Control: no-cache` (как все файлы вне `/assets`), поэтому новая версия сайта
приходит при следующем открытии.

### 113. Итог боя кампании без сети

**Решение:** баннер «Нет подключения» — в каркасе всех страниц (`useNetwork`). Если игрок нажал «Принять»
или «Отклонить» без сети, экран наград ждёт события `online` и отправляет итог сам; баннер «Результат боя
не отправлен» в меню и на листе остаётся, пока итог не на сервере. Без нажатия итог сам не отправляется —
игрок должен увидеть награды.

## Задача 7.2: CI в GitHub Actions (28.09.2026)

### 114. Сверка клиента API

**Решение:** `OpenApiContractIT.exportContract` сохраняет `/v3/api-docs` в `build/openapi.json`; orval
принимает файл через `OPENAPI` (`orval.config.ts`). Клиент из файла совпадает с клиентом из работающего
бэкенда (проверено сравнением каталогов). Тестовый контроллер `GlobalExceptionHandlerTest` попадал в
контракт интеграционных тестов — скрыт `@Hidden`. В CI после перегенерации `git diff --exit-code` и
отсутствие неотслеживаемых файлов в `src/api/generated`.

### 115. Образы в GHCR

**Решение:** публикация образов — отдельный workflow `web-release.yml` по тегу `web-v*` (матрица backend/web,
кэш слоёв GitHub Actions). В `docker-compose.yml` у `backend` и `web` есть `image:
${IMAGE_REGISTRY:-ghcr.io/viktorevdokimov}/primal-*:${IMAGE_TAG:-local}` рядом с `build`: локально
`--build` собирает и помечает образ тегом `local`, на сервере `IMAGE_TAG=web-v…` и `docker compose pull`.
`gradlew` запускается после `chmod +x`: файлы из Windows попадают в git без признака исполняемости.

## Задача 7.3: Эксплуатация (28.09.2026)

### 116. Логи JSON — встроенные средства Spring Boot

**Решение:** вместо своего `logback-spring.xml` — встроенные структурные логи Spring Boot
(`logging.structured.format.console: ecs` в `application-prod.yml`). В Docker профиль `prod` включается
`SPRING_PROFILES_ACTIVE` (по умолчанию `prod`). Поле `requestId` (MDC) попадает в JSON само; в обычном
формате логов (разработка) номер запроса — в `logging.pattern.level`.

### 117. `X-Request-Id`

**Решение:** `RequestIdFilter` — первым в цепочке: номер от прокси принимается, если он короткий и из
безопасных символов (`[A-Za-z0-9._-]{1,64}`), иначе создаётся UUID; номер — в заголовке ответа и в MDC на
время запроса.

### 118. Скрипты копий запускаются через `bash`

**Решение:** в `setup.md` — `bash deploy/backup.sh`, а не `./deploy/backup.sh`: признак исполняемости
теряется при коммите из Windows. `backup.sh` пишет копию во временный файл и переименовывает его только
после успешного `pg_dump` (оборванная копия не выглядит целой); `restore.sh` проверяет архив (`gzip -t`) до
остановки сайта. Пароль и имя базы берутся из окружения контейнера `postgres`, а не из `.env` — в `.env`
есть значения с пробелами (`MAIL_FROM`), которые ломают `source`.

### 119. Заголовки безопасности

**Решение:** к заголовкам Caddy добавлены `Strict-Transport-Security` (браузеры учитывают его только по
HTTPS — локально он безвреден) и `Permissions-Policy`. E2E-смоук проверяет заголовки и `X-Request-Id`.
Запуск по HTTPS с секретами-примерами по-прежнему запрещает `StartupSecretsCheck`.

## Задачи 7.4–7.5: проверка и документация (28.09.2026)

### 120. Устаревший переход главы и подготовка боя из кэша

**Проблема:** найдено E2E в повторных прогонах. TanStack Query показывает закэшированные данные, пока
перезапрашивает свежие: экран перехода главы на миг показывал прошлый переход (глава 1 вместо 2), а
подготовка боя — прошлые главу и `progressSeq`. Нажатие «Принять» или «Начать бой» в этот момент отправило
бы устаревшие данные (переход — `409`, бой — результат, который потом не примут).

**Решение:** у запросов перехода главы и подготовки боя `gcTime: 0` — после ухода с экрана они не
хранятся, и экран всегда ждёт свежий ответ.

### 121. Автоотправка итога при появлении сети

**Проблема:** слушатель события `online` ставился эффектом после отрисовки панели «не отправлен»; если
сеть возвращалась в этот промежуток, итог не уходил сам (E2E изредка падал).

**Решение:** слушатель ставится при открытии экрана наград, а что делать, решает ref, который обновляется
`useLayoutEffect` сразу после рендера.

### 122. Сборка образов при сбое сети Docker Desktop

**Наблюдение:** после аварийного перезапуска Docker Desktop сеть внутри его виртуальной машины зависала:
`npm ci` в образе `web` не завершался (с хоста реестр доступен). Для локальной проверки образ `web`
собирался из готовой сборки фронтенда с хоста временным Dockerfile (вне репозитория); основной Dockerfile
не менялся. Лечится перезапуском Docker Desktop — добавлено в типовые проблемы `setup.md`.

### 123. E2E: ожидания под нагрузкой

**Решение:** окна Mantine открываются и закрываются с анимацией — page object окна «Отклонить» ждёт его
появления перед нажатием и закрытия после. Лист кампании в E2E ждёт до 10 секунд: во втором браузере
service worker при первом открытии скачивает статику.

### 124. «Начать бой» не работал по адресу в локальной сети

**Проблема:** найдено пользователем. С `http://192.168.x.x:8088` (телефон у стола, `setup.md` §2.4)
«Начать бой» ничего не делал: id боя создавался `crypto.randomUUID()`, а браузер даёт его только в
защищённом контексте (HTTPS или `localhost`) — нажатие падало с `TypeError`. Так же по HTTP нет
`navigator.clipboard`: «Копировать» ссылку-приглашение молча не копировал, но сообщал «Ссылка скопирована».

**Решение:**
- `shared/randomId.ts` — UUID v4: `crypto.randomUUID`, а без него — из `crypto.getRandomValues`
  (доступен везде). Им пользуются подготовка экспедиции и боя кампании.
- `shared/copyText.ts` — `navigator.clipboard`, а без него или при отказе — скрытое поле и
  `execCommand('copy')`; не получилось — окно просит скопировать вручную, а не сообщает об успехе.
- E2E `test_insecure_origin.py` открывает сайт по имени `primal.lan`, которое правило резолвера Chromium
  направляет на локальный стек: контекст по-настоящему незащищённый (тест проверяет
  `isSecureContext === false`). До исправления тест падал, после — экспедиция, бой пролога и копирование
  ссылки проходят. Проверено и вручную по `http://192.168.0.31:8088`.
- Работа без сети и установка приложения по `http://IP` невозможны в принципе (service worker — только
  в защищённом контексте) — отмечено в `setup.md` §2.4.

### 125. Ссылка «В главное меню» в списке кампаний

**Проблема:** из списка кампаний нельзя было вернуться в главное меню — только кнопкой «Назад» браузера
(в установленном приложении её нет).

**Решение:** над заголовком списка — ссылка «В главное меню» (`campaigns-to-menu`), в том же виде, что

### 126. Настоящие письма через Mailgun

**Запрос:** отправлять коды входа на настоящую почту через Mailgun (sandbox-домен), ключи — в переменных
окружения.

**Решение:**
- Mailgun подключён по **HTTP API**, а не по SMTP: у пользователя ключ API, а SMTP-пароль Mailgun — другой
  секрет. SMTP остался вторым способом: локально он ведёт в Mailpit, из которого читают коды E2E-тесты.
- Способ выбирает `MAIL_PROVIDER` (`smtp` по умолчанию | `mailgun`). Модуль `mail`: `MailService` собирает
  письмо, доставляет `MailTransport` — `SmtpMailTransport` (прежняя логика) или `MailgunMailTransport`
  (`RestClient`, форма `from/to/subject/text/html`, Basic `api:<ключ>`, таймауты 10 с).
- Переменные `MAILGUN_BASE_URL`, `MAILGUN_DOMAIN`, `MAILGUN_API_KEY`: настоящие значения — только в
  `web/.env` (в `.gitignore`), в `.env.example` — пустые. Без ключа или домена при `mailgun` сервер не
  стартует и называет недостающие переменные. Ключ скрыт в `toString()` настроек и не попадает в текст
  ошибок: в лог пишется только код и ответ Mailgun.
- Отказ Mailgun (`401` — неверный ключ или регион, `403` — адрес не из Authorized Recipients у sandbox)
  пишется в лог предупреждением, как и отказ SMTP; пользователь может запросить код ещё раз.
- Проверено на локальном стеке: запрос кода на `check@example.com` дошёл до Mailgun, ключ принят,
  Mailgun ответил `403` ограничением sandbox — на адреса из Authorized Recipients письма будут доставлены.
- E2E и CI используют `smtp` + Mailpit (CI копирует `.env.example`). Локально при `MAIL_PROVIDER=mailgun`
  перед E2E сервер переключается на `smtp` переменной окружения (`setup.md`, раздел 4).
- Тесты: `MailgunMailTransportTest` (`MockRestServiceServer`: адрес, авторизация, поля формы в UTF-8,
  отказы 401/403/502 без ключа в тексте), `MailConfigTest` (выбор способа, проверка переменных, скрытый
  ключ).

### 127. Вход по логину и паролю вместо кода из письма

**Запрос:** пока убрать вход через почту и сделать вход по логину и паролю; дополнительно можно указать
номер телефона — позже по нему будет восстановление.

**Причина:** бесплатный sandbox-домен Mailgun доставляет письма только на заранее разрешённые адреса
(№ 126) — случайный игрок код не получит.

**Решения:**
- Регистрация сразу выполняет вход; оба запоминают браузер cookie устройства, как раньше вход по коду.
  Гость по ссылке, войдя или зарегистрировавшись, сохраняет устройство и доступы.
- **Логин** — 3–32 символа `[A-Za-z0-9._-]`, хранится в нижнем регистре: без путаницы похожих латинских и
  кириллических букв, `Alice` и `alice` — один логин. Имя (любые буквы) — отдельно, как и раньше.
- **Пароль** — 8–64 символа и не больше 72 байт UTF-8 (предел bcrypt). Хеш — `PasswordEncoder` Spring
  Security с префиксом `{bcrypt}`. Неверный логин и пароль неразличимы и по ответу (`400
  INVALID_CREDENTIALS`, а не 401 — иначе ошибка смены пароля на защищённой странице настроек уводила бы на
  вход), и по времени (фиктивный хеш для неизвестного логина).
- **Перебор:** 20 регистраций и 60 попыток входа в час с IP (`PRIMAL_REGISTRATIONS_PER_IP_HOUR`,
  `PRIMAL_LOGINS_PER_IP_HOUR` вместо лимитов писем и проверок кода), 10 попыток входа и смены пароля за
  15 минут на логин.
- **Телефон** — необязательный, приводится к `+79123456789` (российский номер можно ввести с 8); не
  уникален: восстановление по нему ещё не спроектировано, и один телефон может быть у двух аккаунтов семьи.
  Меняется в настройках, пусто — удалить.
- **Смена пароля** в настройках (текущий + новый дважды): без почты иначе пароль не сменить. Восстановления
  пока нет — забытый пароль администратор сбрасывает в БД (`setup.md`, раздел 6), и пользователь задаёт
  новый на запомненном устройстве.
- **Старые аккаунты** (созданные по почте): миграция V3 дала им логин `user<id>`, пароля нет
  (`passwordSet: false`). Они работают на запомненных устройствах и задают пароль без текущего. Почта
  осталась в БД, но не используется; таблица кодов и секрет `PRIMAL_OTP_PEPPER` удалены. Сайт ещё не
  развёрнут на сервере, так что это касается только локальных баз.
- **Почта** (`mail`, SMTP и Mailgun) оставлена для будущих писем и сейчас ничего не отправляет. E2E больше
  не читают Mailpit: помощник `register` регистрирует пользователя с уникальным логином.

### 128. Номер телефона — логин

**Запрос:** номер телефона используется в качестве логина.

**Решения:**
- Отдельного логина больше нет (миграция V4 удалила столбец `login`): регистрация — номер, пароль и имя,
  вход — номер и пароль. Номер обязателен и уникален; он приводится к `+79123456789`, поэтому
  `8 912 345-67-89` и `+7 (912) 345-67-89` — один аккаунт. Номер не проверяется SMS — такой проверки пока
  нет, как и восстановления.
- **Имя стало обязательным.** Раньше без имени другим участникам показывался логин; теперь это был бы
  номер телефона — личные данные в истории боёв. Аккаунт без имени (созданный по почте) показывается как
  «Игрок».
- **Смена номера** в настройках — это смена логина: занятый номер — `409 PHONE_TAKEN` у поля, удалить номер
  нельзя. Текущий пароль для смены номера не спрашивается: запрос приходит с запомненного устройства,
  как и смена имени.
- Аккаунты по почте (без номера и пароля) задают номер и пароль в настройках. Номера, повторившиеся за
  время, когда телефон был необязательным и неуникальным, V4 оставила только у самого раннего аккаунта.
- Лимит попыток входа считается по нормализованному номеру — другое написание не обходит его.
- **Забытый пароль:** администратор задаёт временный пароль в БД через `pgcrypto` — `crypt(…,
  gen_salt('bf', 10))` с префиксом `{bcrypt}` (`setup.md`, раздел 6). Проверено на локальном стеке: вход с
  временным паролем проходит, старый — нет.

### 129. Сервер за NAT хостинга: Cloudflare Tunnel

**Наблюдение:** у выбранного хостинга сервер стоит за NAT (внутренний адрес `192.168.20.x`); даже с
купленным статическим IP снаружи до него доходит только SSH на нестандартном порту, запросы на 80 и 443
теряются (проверено тестовой страницей и запущенным Caddy). Let's Encrypt для HTTP- и TLS-проверки нужны
именно эти порты.

**Решение:** сайт публикуется через Cloudflare Tunnel (`setup.md` §3.12): контейнер `cloudflared` в
профиле Compose `tunnel` с токеном `CLOUDFLARE_TUNNEL_TOKEN`, HTTPS на домене делает Cloudflare, Caddy
остаётся на `:80` внутри сервера. Чтобы лимиты считались по игрокам, а не по адресу `cloudflared`, Caddy
доверяет `X-Forwarded-For` только из частных сетей (`trusted_proxies static private_ranges`) — прямой
запрос из интернета свой адрес так не подменит. Обычная схема (порты открыты, Caddy сам получает
сертификат) не изменилась.

**Прочее на сервере:** в образе хостинга служба `ufw` была замаскирована — брандмауэр не включался после
перезагрузки; служба размаскирована и включена в автозапуск.

**Отказ от туннеля (30.09.2026):** с телефонов в России сайт через Cloudflare не открывался, хотя из
дата-центра (тоже Россия) и через VPN работал: часть операторов ограничивает соединения с Cloudflare.
Туннель убран: хостинг пробрасывает порты 80 и 443 на статический IP, домен указывает на сервер напрямую,
сертификат получает Caddy — обычная схема `setup.md` §3. Доверие `X-Forwarded-For` из частных сетей убрано
вместе с туннелем: без прокси перед Caddy запрос через `docker-proxy` может прийти с внутреннего адреса, и
тогда клиент подменил бы свой IP и обошёл лимиты на подбор пароля.
